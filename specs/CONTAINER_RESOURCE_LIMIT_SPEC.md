## 1. Resource Limit Ceilings

To protect against Denial of Service (DoS), catastrophic regex backtracking (ReDoS), zip bomb memory expansion, and fork bombs, strict resource ceilings are enforced for every container:

| Service | CPU Limit | Memory Limit | Swap Limit | PIDs Limit | Root Filesystem | Tmpfs Size |
|---|---|---|---|---|---|---|
| **`scanner`** | `2.0` cores | `1536M` (1.5 GB) | `1536M` (Disabled) | `100` | Read-only (`ro`) | `64M` (`/tmp`) |
| **`backend`** | `1.5` cores | `1024M` (1.0 GB) | `1024M` (Disabled) | `150` | Read-write | N/A |
| **`mongodb`** | `1.0` cores | `1024M` (1.0 GB) | `1024M` (Disabled) | `100` | Read-write | N/A |
| **`frontend`** | `1.0` cores | `1024M` (1.0 GB) | `1024M` (Disabled) | `100` | Read-write | N/A |

## 2. Docker Compose Configuration Syntax

To guarantee compatibility across Compose v2 and Swarm/orchestrator deployments, resource limits are specified using both standard Compose v2 attributes and `deploy.resources`:

```yaml
scanner:
  cpus: 2.0
  mem_limit: 1536m
  memswap_limit: 1536m
  pids_limit: 100
  read_only: true
  tmpfs:
    - /tmp:rw,noexec,nosuid,size=67108864
  deploy:
    resources:
      limits:
        cpus: '2.0'
        memory: 1536M
        pids: 100
      reservations:
        cpus: '0.5'
        memory: 512M
```

---

## 3. OOM & Process Termination Semantics

1. **OOM Killer Handling:**
   - If scanner memory exceeds 1536 MB, the kernel OOM killer terminates the offending subprocess or container.
   - Swap is disabled (`memswap_limit == mem_limit`) to prevent catastrophic disk thrashing.
2. **PID Limit Handling:**
   - PIDs limit of 100 prevents fork bombs generated by hostile code or recursive subprocess spawning.
3. **Execution Timeouts:**
   - Per-scanner adapter timeout: 60 seconds hard ceiling.
   - Global orchestrator scan timeout: 300 seconds (5 minutes).
