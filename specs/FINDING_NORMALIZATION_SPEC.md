## 1. Executive Summary & Purpose

Every security scanner in the Thread Trace toolchain (Semgrep, Bandit, Gitleaks, OSV-Scanner, Custom Rules) emits results in distinct, incompatible formats with differing field names, severity scales, line references, and metadata structures.

The **Finding Normalization Specification** establishes a single canonical data contract. All scanner modules must translate raw scanner output into this normalized representation before findings are persisted in the database, passed to the AI explanation service, or served via API endpoints to the frontend.

This specification respects the existing backend implementation in `backend/app/schemas/finding.py` authored by Dev B, ensuring full backwards compatibility while formalizing field semantics and proposing future type enhancements.

---

## 2. Canonical Finding Data Model

The canonical finding model is implemented in `backend/app/schemas/finding.py` as:

```python
from typing import Literal
from pydantic import BaseModel, Field

class Finding(BaseModel):
    id: str
    domain: str
    rule_id: str
    title: str
    severity: Literal["critical", "high", "medium", "low"]
    file: str
    line: int | None = None
    evidence: str
    confidence: str
    explanation: str | None = None
    recommendation: str | None = None
    tool: str
```

## 3. Detailed Field Specifications & Normalization Rules

### 3.1 `id` (Finding Identifier)
- **Type:** `str` (Required)
- **Format:** `find_<uuid4_hex>` or deterministic hash `tt-<scan_id>-<sha256(tool:rule:file:line)>`
- **Semantics:** Unique identifier for each finding instance within a scan job.
- **Normalization Rule:**
  - If generated by scanner adapter: Must use `uuid.uuid4().hex` prefixed with `find_` (e.g., `find_a1b2c3d4e5f67890`).
  - Must remain immutable throughout the scan lifecycle, persistence, and reporting.

### 3.2 `domain` (Cybersecurity Domain)
- **Type:** `str` (Required)
- **Allowed Values:** Must exactly match one of the five canonical domain titles defined in `specs/CYBERSECURITY_DOMAINS_SPEC.md`:
  1. `"Secrets & Sensitive Information Management"`
  2. `"Web Application Security"`
  3. `"Network & Communication Security"`
  4. `"Authentication & Access Control"`
  5. `"Dependency & Configuration Security"`
- **Normalization Rule:**
  - Scanner adapters must map tool-specific categories (e.g., Bandit `B5xx` -> `"Network & Communication Security"`, Gitleaks -> `"Secrets & Sensitive Information Management"`, OSV -> `"Dependency & Configuration Security"`) into these exact strings.

### 3.3 `rule_id` (Rule Identifier)
- **Type:** `str` (Required)
- **Semantics:** Specific identifier of the rule or advisory that triggered the finding.
- **Normalization Rule:**
  - Preserve original scanner rule identifiers prefixed by tool namespace where appropriate:
    - Semgrep: `semgrep.<check_id>` (e.g., `semgrep.python.lang.security.injection.sql`)
    - Bandit: `bandit.<test_id>` (e.g., `bandit.B608`)
    - Gitleaks: `gitleaks.<rule_id>` (e.g., `gitleaks.aws-access-key-id`)
    - OSV-Scanner: `osv.<advisory_id>` (e.g., `osv.GHSA-xxxx-yyyy-zzzz` or `osv.CVE-2023-45803`)
    - Custom Rules: `custom.<rule_id>` (e.g., `custom.fastapi-missing-rate-limit`)

### 3.4 `title` (Finding Title)
- **Type:** `str` (Required)
- **Semantics:** Concise, human-readable summary of the vulnerability (max 150 characters).
- **Normalization Rule:**
  - Must not contain raw code snippets, tracebacks, or file paths.
  - Capitalize like a title (e.g., `"SQL Query Constructed with Untrusted String Formatting"`).
  - Strip redundant prefixes like `"ERROR:"` or `"[WARN]"`.

### 3.5 `severity` (Vulnerability Severity)
- **Type:** `Literal["critical", "high", "medium", "low"]` (Required)
- **Semantics:** Potential impact of the flaw if exploited.
- **Normalization Rule:**
  - Must be lowercase string strictly matching one of the four literal values.
  - Tool-specific mapping defined in `specs/SEVERITY_CONFIDENCE_SPEC.md`.

### 3.6 `file` (File Path)
- **Type:** `str` (Required)
- **Semantics:** Relative path to the affected source or configuration file within the scanned workspace.
- **Normalization Rule:**
  - Must use forward slashes (`/`) regardless of host operating system (POSIX & Windows compatible).
  - Must NOT contain leading slashes (`/`), `./`, or parent directory traversal sequences (`../`).
  - Strip the temporary workspace prefix (e.g., `/tmp/thread-trace/scans/123/src/app.py` -> `src/app.py`).

### 3.7 `line` (Line Number)
- **Type:** `int | None` (Optional, defaults to `None`)
- **Semantics:** 1-indexed line number in `file` where the flaw or starting AST node is located.
- **Normalization Rule:**
  - Must be a positive integer (`>= 1`) when identified.
  - Set to `None` when the finding applies to the entire file (e.g., missing security header in configuration, whole-manifest dependency vulnerability in `requirements.txt`).
  - Never use `0` or negative integers.

### 3.8 `evidence` (Sanitized Code Snippet / Context)
- **Type:** `str` (Required)
- **Semantics:** Extracted source code line, surrounding context snippet, or dependency advisory statement illustrating the flaw.
- **Normalization Rule:**
  - **MANDATORY REDACTION:** Any detected API key, password, token, or secret string MUST be redacted (e.g., replacing sensitive characters with `[REDACTED]` or `AKIA****************`).
  - Length Bounding: Truncated to a maximum of 1,000 characters to prevent excessive memory usage or API payload bloat.
  - Missing Evidence Fallback: If the tool does not provide code context (e.g., manifest-level SCA), provide a structured description (e.g., `"Package 'urllib3' version 1.26.17 matched vulnerability advisory CVE-2023-45803."`).

### 3.9 `confidence` (Detection Confidence)
- **Type:** `str` (Required; semantically `"high" | "medium" | "low"`)
- **Semantics:** Degree of certainty that the detection is an accurate true positive.
- **Normalization Rule:**
  - Normalized to lowercase `"high"`, `"medium"`, or `"low"`.
  - Detailed classification criteria provided in `specs/SEVERITY_CONFIDENCE_SPEC.md`.

### 3.10 `explanation` (AI-Assisted or Extended Explanation)
- **Type:** `str | None` (Optional, defaults to `None`)
- **Semantics:** In-depth explanation of why the finding is insecure, potential exploit scenarios, and business impact.
- **Normalization Rule:**
  - Initialized to `None` or scanner rule documentation by Dev C's scanner modules.
  - Enriched asynchronously by Dev B's AI service (`ai_service.py`) during post-processing.

### 3.11 `recommendation` (Remediation Guidance)
- **Type:** `str | None` (Optional, defaults to `None`)
- **Semantics:** Actionable instructions for developers to fix the vulnerability.
- **Normalization Rule:**
  - Initialized with standard rule remediation from the scanner tool if available.
  - Can be refined or expanded by Dev B's AI service.

### 3.12 `tool` (Scanner Identity)
- **Type:** `str` (Required)
- **Semantics:** Identifier of the scanner module that generated the finding.
- **Standardized Values:**
  - `"semgrep"`
  - `"bandit"`
  - `"gitleaks"`
  - `"osv-scanner"`
  - `"custom-rules"`

## 4. Normalization Mapping Table by Tool

| Field | Semgrep Raw Mapping | Bandit Raw Mapping | Gitleaks Raw Mapping | OSV-Scanner Raw Mapping |
|---|---|---|---|---|
| `id` | Generated UUID | Generated UUID | Generated UUID | Generated UUID |
| `domain` | Mapped via rule tags | Mapped via test ID range | `"Secrets & Sensitive Information Management"` | `"Dependency & Configuration Security"` |
| `rule_id` | `semgrep.<check_id>` | `bandit.<test_id>` | `gitleaks.<RuleID>` | `osv.<vulnerability.id>` |
| `title` | `extra.message` (first sentence) | `issue_text` | `Description` | `summary` or `details` (first line) |
| `severity` | `ERROR` -> `high`/`critical`, `WARNING` -> `medium`, `INFO` -> `low` | `HIGH`/`MEDIUM`/`LOW` -> mapped | `critical` (private keys, cloud keys) or `high` | Mapped from CVSS score |
| `file` | Relative `path` | Normalized `filename` | Relative `File` | Relative `source` path |
| `line` | `start.line` | `line_number` | `StartLine` | `None` |
| `evidence` | `extra.lines` (sanitized) | `code` (sanitized) | `Match` (secret redacted) | Vulnerable package & version statement |
| `confidence` | `extra.metadata.confidence` | `issue_confidence` | `"high"` (format/entropy match) | `"high"` (lockfile) or `"medium"` (manifest) |
| `tool` | `"semgrep"` | `"bandit"` | `"gitleaks"` | `"osv-scanner"` |

### 5.1 Preservation of Existing Implementation
Dev C affirms that `backend/app/schemas/finding.py` is fully compatible with this normalization specification. Dev C has **NOT modified** `backend/app/schemas/finding.py` in Phase 1, preserving all existing code and passing unit tests (`backend/tests/test_findings.py`).

### 5.2 Proposed Enhancements for Dev B Agreement (Future Phase Consideration)
To further improve type safety and frontend integration in Phase 3 or Phase 6, Dev C proposes the following non-breaking enhancements for Dev B's consideration:

1. **Strict Confidence Typing:**
   ```python
   # Proposed future refinement:
   confidence: Literal["high", "medium", "low"] = "medium"
   ```
2. **Canonical Domain Literal:**
   ```python
   # Proposed future refinement:
   DomainType = Literal[
       "Secrets & Sensitive Information Management",
       "Web Application Security",
       "Network & Communication Security",
       "Authentication & Access Control",
       "Dependency & Configuration Security",
   ]
   domain: DomainType
   ```
3. **Optional Line Range & Column Metadata:**
   ```python
   line_end: int | None = None
   cwe: list[str] = Field(default_factory=list)
   ```

*Agreement Protocol:* These proposals remain advisory and are explicitly marked **STATUS: PENDING DEV B APPROVAL**. Dev C will NOT modify `backend/app/schemas/finding.py`. Until Dev B formally approves and schedules schema updates, all scanner modules implemented in Phase 2 will produce dictionaries that strictly satisfy the current `Finding` model.

### 5.3 Frontend Consumption Alignment (Dev A)
Dev A consumes the normalized `Finding` objects across several Next.js components:
- `frontend/src/components/findings/VulnerabilityCard.jsx`: Displays finding summary cards (title, severity, domain, file, line, confidence).
- `frontend/src/components/findings/FindingDetails.jsx`: Displays extended vulnerability view, including `evidence`, `explanation`, and `recommendation`.
- `frontend/src/components/findings/DomainFilter.jsx`: Filters findings by domain.
- `frontend/src/components/dashboard/SeveritySummary.jsx`: Aggregates findings by severity tier.

Dev C guarantees that:
1. `file` is always a clean relative path with forward slashes (e.g. `app/main.py`), preventing broken UI links.
2. `line` is either a valid positive integer or `None` (for manifest/package-level findings).
3. `evidence` is pre-redacted in memory so raw secrets are never rendered in the browser.
4. `severity` strictly adheres to `"critical" | "high" | "medium" | "low"`, ensuring UI severity badge color styling maps cleanly.
